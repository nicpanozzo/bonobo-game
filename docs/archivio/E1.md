# E1 · Server in produzione e anteprima giocabile per ogni PR

Issue: #19 · ondata 1 · [piano](../piano-prodotto.md)

**Obiettivo:** il gioco ha un server fisso a cui l'app e la build web si collegano da sole, e ogni PR ha un link per provarla nel browser.
**Perché serve a un prodotto professionale:** oggi si gioca solo se un amico apre `bonobo-server` con il tunnel (`src/server/host.ts`) e il link cambia ogni volta; la build web su GitHub Pages, senza `?server=`, prova `localhost:3000` (`DEFAULT_SERVER` in `godot/scripts/main.gd`). Un prodotto ha un indirizzo stabile e qualcuno che se ne accorge quando cade.

**Dove siamo:** il passo 1 (CI in `.github/workflows/ci.yml`) e il passo 4 (test in `src/**/*.test.ts`) di questa issue sono fatti. Restano il deploy (passo 2) e l'anteprima (passo 3), che qui diventa l'ambiente `staging`. `render.yaml` non esiste ancora. Il server per le serate in casa (`host.ts`, Release `bonobo-server-*`) resta com'è: è il ripiego se la produzione cade.

## Passi

### Passo 1: hosting gratuito e indirizzo fisso
- `render.yaml` alla radice: servizio web Node, build `npm ci && npm run build`, start `npm start`, controllo di salute su `/health`, deploy solo a CI verde (`autoDeployTrigger: checksPass`, se Render lo offre sul piano scelto).
- Disco persistente o `LEADERBOARD_FILE` su un percorso che sopravvive al deploy: oggi `data/classifica.json` (`src/server/leaderboard.ts`) si perderebbe a ogni rilascio.
- `godot/scripts/main.gd`: nuova costante `PRODUCTION_SERVER` (l'indirizzo https del servizio) usata al posto di `DEFAULT_SERVER` quando il gioco è esportato (`OS.has_feature("template")`); in editor resta `localhost:3000`.
- Nella PR, i passi che fa un umano: account, piano, variabile `DISCORD_WEBHOOK_URL`, dominio se c'è.
- **Fatto quando:** dopo un merge su `main` con CI verde, `curl https://<indirizzo>/health` risponde entro 10 minuti con il commit nuovo; la build web su Pages e l'app desktop entrano in una stanza senza scrivere il server.

### Passo 2: anteprima giocabile per ogni PR
- `.github/workflows/anteprima.yml` (nuovo): su ogni PR che tocca `godot/` esporta la build web e la pubblica su Pages in `/pr/<numero>/`, collegata al server di produzione; commenta nella PR il link "prova nel browser" e lo aggiorna a ogni push. Le build si cancellano alla chiusura della PR.
- Se la PR cambia anche il server, il commento spiega come provarla con `npm run host` (il tunnel di oggi) e `?server=`.
- **Fatto quando:** aprendo una PR che cambia un colore in `world_view.gd`, entro pochi minuti nella PR c'è un link che apre il gioco nel browser con la modifica, e due persone ci giocano insieme senza installare niente.

### Passo 3: `/health` con versione e stanze
- `/health` aggiunge `version` (da `package.json`), `commit`, `rooms`, `players`; restano i campi di oggi (`app.yml` lo interroga già). Logica in nuovo `src/server/health.ts` con test.
- **Fatto quando:** `curl https://<indirizzo>/health` mostra il commit di `main` e `players: 2` con due client in una stanza.

## Rischi e decisioni aperte
- **Fase precoce, quindi gratis:** si parte con un piano gratuito (Render o simile con WebSocket). Si addormenta dopo 15 minuti e il primo accesso impiega circa un minuto: in questa fase va bene. Allarmi, log strutturati e ambiente di staging sono rimandati a quando ci sarà un pubblico.
- **Regione:** il server deve stare in Europa (Francoforte o simile), altrimenti il lag è peggio della serata in casa.
- Le stanze vivono in memoria: un deploy chiude le partite in corso. Fino a E5 (riconnessione) conviene non mergiare durante le serate o deployare di notte.
- La classifica su file regge un solo processo: niente scalare su più istanze.
- Il cron di GitHub Actions può ritardare anche di molto: se non basta, un servizio esterno gratuito di uptime (lo configura un umano).

## Per gli agenti
- **Stato:** pronto (passo 1, serve un umano per l'account); passo 2 pronto anche subito, con il server di oggi; passo 3 dopo il passo 1.
- **Corsia:** Infrastruttura.
- **File suoi:** `render.yaml`, `.github/workflows/anteprima.yml`, `.github/workflows/pages.yml` (solo per fare spazio a `/pr/`), `src/server/health.ts` e il suo test; in `main.gd` solo `PRODUCTION_SERVER`.
- **Non toccare:** `src/shared/physics/`, `types.ts` (nessun cambio di protocollo qui), `src/server/host.ts`, la logica di `join` in `index.ts` (corsia Rete, E4 e E5).
- **Dipende da:** niente per il passo 1, ma serve un umano per l'account e il piano. Coordinarsi con E4 su `index.ts` e con E2 sul campo `version` di `/health`.
- **Come provarlo:** `npm run typecheck && npm test && npm run build`; in locale `npm start` e `curl localhost:3000/health`; poi due istanze Godot esportate (o la build web su Pages) che entrano nella stessa stanza sul server di produzione senza scrivere l'indirizzo.
